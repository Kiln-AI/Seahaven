# `/ws` and `/mcp` log a full traceback on every clean websocket disconnect

## Summary

Both websocket endpoints in `HTTPEnvServer` close the connection in a `finally` block guarded by `except RuntimeError`, but the exception a closed peer actually raises is `starlette.websockets.WebSocketDisconnect`, not `RuntimeError`. The guard never fires, the exception escapes the ASGI app, and uvicorn logs `ERROR: Exception in ASGI application` with a full traceback — for a session that ended normally. `WebSocketDisconnect` is already imported in the file, so the fix is one name added to each of two tuples.

This isn't a rare race. OpenEnv's own `EnvClient._disconnect_async` sends `{"type": "close"}` and then calls `ws.close()` in the very next line, so the CLOSE frame usually reaches uvicorn before the server's `finally` block gets there (it does an `await self._destroy_session(...)` first, which yields). So the stock client trips this on close, every time. On a server handling many concurrent sessions, the error log — the one an operator greps when something is actually wrong — fills with tracebacks from disconnects that were completely clean. We measured it in our own test suite before working around it locally: one run of one test file produced **518** of these tracebacks, all from ordinary session teardown, none of them real errors.

## Cause

All references are to `src/openenv/core/env_server/http_server.py`. Checked against the released **0.4.2** and current **`main`** (`da5929566e99c8eb376a47042b316cb13c0aae29`) — the file is byte-identical between the two, so this is not fixed on `main`.

`WebSocketDisconnect` is already imported from `fastapi`, [line 43](https://github.com/huggingface/OpenEnv/blob/main/src/openenv/core/env_server/http_server.py#L43).

**`/mcp` endpoint** (`mcp_websocket_endpoint`), [lines 1250-1255](https://github.com/huggingface/OpenEnv/blob/main/src/openenv/core/env_server/http_server.py#L1250-L1255):

```python
            finally:
                if session_id:
                    await self._destroy_session(session_id)
                try:
                    await websocket.close()
                except RuntimeError:
                    pass
```

**`/ws` endpoint** (`websocket_endpoint`), [lines 1690-1695](https://github.com/huggingface/OpenEnv/blob/main/src/openenv/core/env_server/http_server.py#L1690-L1695) — identical shape:

```python
            finally:
                if session_id:
                    await self._destroy_session(session_id)
                try:
                    await websocket.close()
                except RuntimeError:
                    pass
```

Why the peer is usually already gone by the time `/ws` reaches its own `close()`: `EnvClient._disconnect_async` (`env_client.py`, around lines 552-557) does

```python
await ws.send(json.dumps({"type": "close"}))
await ws.close()
```

back to back, in the same TCP flight. The server's handler breaks out of its receive loop on the `"close"` message, then `await`s `_destroy_session(...)` — which yields — and by the time control returns to its own `close()`, uvicorn has already processed the client's CLOSE frame and torn the transport down. Closing an already-closed connection is what turns into `WebSocketDisconnect` here: uvicorn raises `ClientDisconnected` (an `OSError`), and starlette's `WebSocket.close()` converts any `OSError` into `WebSocketDisconnect`. `except RuntimeError` never sees it.

## Suggested fix

```diff
             finally:
                 if session_id:
                     await self._destroy_session(session_id)
                 try:
                     await websocket.close()
-                except RuntimeError:
+                except (RuntimeError, WebSocketDisconnect):
                     pass
```

Applied at both sites (1255 and 1695). No new import needed — `WebSocketDisconnect` is already pulled in from `fastapi` at line 43.

As a second, optional improvement on the client side: `EnvClient._disconnect_async` could send the close message and then wait for the server's own close frame instead of closing immediately. A client that does that never provokes this at all — the server gets to call `close()` on a still-open connection and the handshake finishes cleanly with no exception on either end. That's a bigger change than the one-line server fix above, so we're mentioning it rather than asking for it, but it's worth knowing the server-side fix isn't the only way to get a quiet log.
