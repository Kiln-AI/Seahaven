HTTP `/reset`, `/step`, `/state` build a fresh Environment per request and cannot hold an episode

## Summary

`HTTPEnvServer`'s `/reset`, `/step`, and `/state` handlers each instantiate a brand-new `Environment` via `self._env_factory()` and close it in a `finally` block before returning. Every HTTP request therefore runs against its own throwaway environment instance. `POST /reset` resets one instance, `POST /step` steps a different instance, and `GET /state` reads a third. None of them observe each other's effects, so these three routes cannot represent an episode over HTTP — they return plausible-looking but meaningless responses.

Code (current `main`, `src/openenv/core/env_server/http_server.py`):
- `reset_handler`: `_env = self._env_factory()` at line 674, `_env.close()` in `finally` at line 695
- `step_handler`: `_env = self._env_factory()` at line 709, `_env.close()` in `finally` at line 733
- `get_state_handler`: `_env = self._env_factory()` at line 1347, `_env.close()` in `finally` at line 1351
- `get_metadata_handler`: `_env = self._env_factory()` at line 1354

This is on `main` at `da59295` (`0.4.3.dev0`) and is byte-identical to the released `0.4.2`, so it affects the current release as well.

## Minimal reproduction

Run any stock env's HTTP server (`grid_world_env` shown here) and drive the episode over HTTP:

```bash
curl -s -X POST http://localhost:8000/reset
# {"observation":{"metadata":{},"x":0,"y":0,"message":"Welcome to Grid World! Goal is at [4, 4]."},"reward":0.0,"done":false,"metadata":null}

curl -s -X POST http://localhost:8000/step -H "Content-Type: application/json" \
  -d '{"action": {"action": "DOWN"}}'
# {"observation":{"metadata":{},"x":1,"y":0,"message":"Keep going..."},"reward":-0.1,"done":false,"metadata":null}

curl -s -X POST http://localhost:8000/step -H "Content-Type: application/json" \
  -d '{"action": {"action": "DOWN"}}'
# {"observation":{"metadata":{},"x":1,"y":0,"message":"Keep going..."},"reward":-0.1,"done":false,"metadata":null}

curl -s http://localhost:8000/state
# {"episode_id":"c1977bfa-d32f-4e31-84e1-fb6d32e5686c","step_count":0}
```

(Output above is from actually running `envs/grid_world_env/server/app.py` locally and curling it.)

**Expected:** the second `/step DOWN` moves the agent again (`x=2`), and `/state` reports `step_count: 2` and the position reached by the two steps.

**Actual:** the second `/step` returns the exact same observation as the first (`x=1`, unchanged), because it runs against a fresh environment that starts at `[0, 0]` again. `/state` reports `step_count: 0` — the two steps never happened as far as `/state` is concerned. None of the three responses describe one consistent environment.

`envs/grid_world_env/server/app.py` still carries a comment and commented-out line from when this was true:
```python
# Create single environment instance
# This is reused for all HTTP requests.
# env = GridWorldEnvironment()
```

## This is a regression

History on `main` (`git log`/`git show` against a full clone of `huggingface/OpenEnv`):

| Commit | Date | Summary | HTTP handler state |
|---|---|---|---|
| `274b0de` | 2025-10-08 | "add http server wrapper for gymnasium APIs: step, reset, state" | `HTTPEnvServer.__init__` sets `self.env = env()`; handlers call `self.env.reset()` / `self.env.step()`. One env per process — stateful. |
| `85c47c6` | 2025-12-04 | "Add WebSocket support for environment interactions and enhance HTTP server capabilities" | HTTP handlers still use `self.env`. Still stateful. |
| `438f966` | 2025-12-10 | "refactor: enforce env factory usage and drop instance mode" | Still `self.env = env()` under the hood. Still stateful. |
| `86a222d` | 2025-12-12 | "refactor: core types for better inference and fix async detection" | Deletes `self.env = env()` and rewrites `reset_handler`, `step_handler`, `get_state_handler`, `get_metadata_handler` to build `_env = self._env_factory()` and `_env.close()` per call. **This is where the regression was introduced.** The commit message is about generics (`ActT`/`ObsT`/`StateT`) and async-method detection (`reset_async`/`step_async`); it does not mention episode semantics. `self.env` had also been used for `hasattr(self.env, "reset_async")` probing at construction time — when that was replaced with per-call `is_async` checks on a locally-built `_env`, every handler that depended on `self.env` for state was left building a throwaway instance instead. |
| `402d144` | 2025-12-15 | "rename in core to envclient" | Deletes `src/openenv/core/http_env_client.py` (236 lines), whose docstring described "a single env worker exposing: POST /reset, POST /step". There is no HTTP-transport client class left in `0.4.2`/`main` — `EnvClient` and its subclasses speak WebSocket only. |

## User impact

`envs/calendar_env/server/openenv_wrapper/custom_http_server.py` subclasses `HTTPEnvServer` and, in `__init__`, does:

```python
# Create a persistent environment instance for HTTP endpoints
# The parent class stores env_factory in self._env_factory
# We create one instance for the HTTP endpoints (not WebSocket)
if callable(self._env_factory):
    self.env = self._env_factory()
else:
    self.env = self._env_factory
```

and then fully overrides `register_routes` to reimplement `/reset`, `/step`, and `/state` against that single persistent `self.env` — hand-restoring the exact semantics `86a222d` removed. This is a first-party environment working around the base class rather than relying on it.

## Why it isn't caught by existing checks

- `envs/grid_world_env/test_grid_world.sh` posts `/reset`, posts one `/step`, then greps `/state` for the literal string `"step_count"`. A fresh env's state (`step_count: 0`) still contains that substring, so the check passes regardless of whether state actually persisted.
- The `openenv` CLI's `mode_endpoint_consistency` validation criterion (`src/openenv/cli/_validation.py`, around lines 379-404) only checks whether `/reset`, `/step`, `/state` appear in the generated OpenAPI `paths`, never whether they behave statefully.

## Docs currently contradict each other

- `tutorial/02-deployment.md` (around lines 44-54) labels `/reset` and `/step` "(stateless)" in the endpoint table and says "HTTP endpoints are available for debugging or stateless use cases."
- `docs/source/environments/grid_world.md:115` still says: "HTTP requests are stateless, so the environment instance must remember the agent's position between calls" — describing the pre-regression behavior as if it were current.
- `docs/source/guides/simulation-vs-production.md` still documents `/reset` / `/step` / `/state` as the simulation-mode episode loop without qualification.

## Suggested fix

Per the maintainers' direction that this needs cleanup rather than necessarily restoring statefulness, the two reasonable options are:

1. **Make the routes fail loudly and informatively** instead of silently returning wrong data — e.g. respond with a clear error explaining that HTTP episode control is deprecated, that the endpoint cannot hold an episode because it builds a fresh environment per request, and pointing at the `/ws` WebSocket transport (or MCP `/mcp` sessions) as the supported alternative. This would also note that the regression was introduced in `86a222d`.
2. **Remove `/reset`, `/step`, and `/state` (and `/metadata`, which has the same per-request pattern) entirely** if per-request semantics are not going to be supported.

Whichever is chosen, `tutorial/02-deployment.md`, `docs/source/environments/grid_world.md`, and `docs/source/guides/simulation-vs-production.md` need to be updated so they stop describing behavior the code no longer has, and `envs/calendar_env`'s workaround should be revisited once the base class's intended behavior is settled.
