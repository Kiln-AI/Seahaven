# `ERROR: Exception in ASGI application` on every clean disconnect

Investigation, 2026-09-14. Versions in `/home/user/Seahaven/.venv`:
openenv 0.4.2, uvicorn 0.52.4, starlette 1.6.0, websockets 17.1, fastapi 0.141.1,
CPython 3.14.

## Lead finding: yes, our client provokes it, and a client-side fix removes it

The traceback is **not** inevitable. It is caused by the client closing the TCP
socket before the server's handler reaches its own `close()`. A client that
sends `{"type": "close"}` and then **waits for the server to hang up first**
produces a clean 1000/1000 handshake and no log line at all.

Measured, `tests/test_server.py` run with `-s` (uvicorn's stderr uncaptured):

| client close sequence | `Exception in ASGI application` count |
| --- | --- |
| stock `EnvClient._disconnect_async` | **518** |
| polite close (wait for server) | **1** (the one raw-socket test, below) |

Both runs pass (`exit=0`). Cost: none — 20 full sessions took 0.287 s stock vs
0.268 s polite (14.4 vs 13.4 ms/session); `close()` against an already-dead
server returns in 0.001 s.

### Mechanism

`EnvClient._disconnect_async`
(`.venv/.../openenv/core/env_client.py:544-560`) does:

```python
await ws.send(json.dumps({"type": "close"}))  # line 552
await ws.close()  # line 557  <-- immediately
```

`websockets`' `ws.close()` sends a CLOSE frame right behind the text frame, in
the same TCP flight.

The server's `/ws` handler
(`.venv/.../openenv/core/env_server/http_server.py:1607-1698`) does:

```python
case "close":
    msg = WSCloseMessage(**message_dict)
    break                                   # 1605-1607
...
finally:
    if session_id:
        await self._destroy_session(session_id)   # 1691-1692  <-- awaits, yields
    try:
        await websocket.close()                   # 1694
    except RuntimeError:                          # 1695  <-- wrong exception
        pass
```

`_destroy_session` is an `await`, so the handler yields. In that window uvicorn
processes the client's CLOSE frame, tears the transport down, and sets
`self.disconnected = True`
(`uvicorn/protocols/websockets/websockets_sansio_impl.py:151`, in
`connection_lost`). The handler resumes and calls `close()`:

- `websockets_sansio_impl.py:436` — `raise ClientDisconnected()`
- `ClientDisconnected` is an `OSError` (`uvicorn/protocols/utils.py:10`)
- `starlette/websockets.py:88-89` — `except OSError: raise WebSocketDisconnect(code=1006)`
- escapes `http_server.py:1694`, because the guard is `except RuntimeError` and
  `WebSocketDisconnect` is not one — and because an exception raised *inside* a
  `finally` is not caught by that same `try`'s `except WebSocketDisconnect: pass`
  at line 1664.
- propagates out through fastapi/starlette to `run_asgi`, which logs
  `ERROR: Exception in ASGI application` on the `uvicorn.error` logger.

Confirmed by three probe modes against a real server:

| client behaviour | result |
| --- | --- |
| `with SeahavenClient(...) as env:` (textbook) | **ERROR + traceback** |
| explicit `env.close()` | **ERROR + traceback** |
| raw socket, `ws.close()` with no `{"type":"close"}` | **ERROR + traceback** |
| raw socket, send `{"type":"close"}` then wait | **silent**, `ConnectionClosedOK: received 1000 (OK); then sent 1000 (OK)` |

The fourth row is the fix: the server closes first with 1000 and the client
answers. Note the third row — a client that never sends `{"type":"close"}` also
trips it, so this is not "our client skips the handshake"; it is that the stock
handshake does not *wait*.

### The change

In `src/seahaven/openenv/client.py`, override `_disconnect_async`:

```python
import asyncio
import json

# How long a close waits for the server to hang up before falling back to the
# abrupt close the stock client always did.
CLOSE_TIMEOUT = 5.0


    async def _disconnect_async(self) -> None:
        ws = self._ws
        if ws is not None and self._ws_loop is asyncio.get_running_loop():
            try:
                await ws.send(json.dumps({"type": "close"}))
                await asyncio.wait_for(ws.wait_closed(), timeout=CLOSE_TIMEOUT)
            except Exception:
                pass  # best effort; super() tears the socket down either way
        await super()._disconnect_async()
```

- The `_ws_loop is get_running_loop()` guard mirrors the base client's own
  `same_loop` check at `env_client.py:549`; without it a cross-loop close would
  touch a socket bound to a dead loop.
- `super()._disconnect_async()` still runs, so a server that never answers is
  closed exactly as before, and `self._ws` / `self._ws_loop` are still cleared.
- Covers every path: `close()` -> `_close_async` -> `_disconnect_async`
  (`env_client.py:889-901`), `__exit__`/`__aexit__`, `.sync()`, and child
  sessions (`new_session` builds `type(self)(...)` at `env_client.py:409`, so
  children are `SeahavenClient` too).

Downside: `close()` now blocks until the server has finished `_destroy_session`
(bounded by `CLOSE_TIMEOUT`). That is arguably a feature — teardown becomes
deterministic — but it is a behaviour change.

### Gap this leaves

It only fixes *our* client. A harness driving the server with stock
`GenericEnvClient`, or a raw socket, still trips it. `tests/test_server.py:434`
(`async with ws_connect(...)`) is exactly that case, and is the single remaining
error in the patched run.

### Does our test helper provoke it?

`tests/serving.py:39` serves at `log_level="warning"` — **which does not
suppress this**, see below. The suite emits 518 of these tracebacks; they are
invisible only because pytest captures stderr and discards it on passing tests.
`tests/serving.py` itself shuts the server down correctly (`should_exit` +
join); the errors come from the clients in `tests/test_server.py`.

## Workarounds, ranked

### 1. Server-side ASGI middleware — RECOMMENDED alongside the client fix

**Verified to work.** The exception propagates all the way out of the FastAPI
app (the traceback passes through `starlette/applications.py:96` and
`uvicorn/middleware/proxy_headers.py:63`), so middleware does see it. Both
placements were tested and both silenced it completely (0/3 errors):

- wrapping the object `create_app()` returns, and
- `fastapi_app.add_middleware(...)` — **preferred**, because it keeps
  `seahaven.openenv.app()`'s `FastAPI` return type, and so every deployment
  (`serve`, `tests/serving.py`, a hub world's `openenv_app.py`) gets it without
  each having to remember to wrap.

```python
class _SwallowWebSocketDisconnect:
    """Absorb the disconnect OpenEnv's /ws handler lets escape at close."""

    def __init__(self, app):
        self.app = app

    async def __call__(self, scope, receive, send):
        if scope["type"] != "websocket":
            return await self.app(scope, receive, send)
        try:
            await self.app(scope, receive, send)
        except WebSocketDisconnect:
            pass
```

Downsides, honestly: it silences `WebSocketDisconnect` from *anywhere* in a
websocket handler, not just line 1694. That is a much smaller loss than it
sounds — a `WebSocketDisconnect` escaping a websocket route means the peer went
away, which is never an actionable server error — but it is broader than the one
line. It touches no other library's logger, needs no exception-message or
module-name matching, and cannot swallow an HTTP-side error (the `scope["type"]`
guard). It also covers third-party clients, which the client fix does not.

### 2. Upstream PR — worth contributing, does not help us today

One line at `http_server.py:1695` (and again at 1255):

```python
except (RuntimeError, WebSocketDisconnect):
    pass
```

Correct and minimal, and `WebSocketDisconnect` is already imported at line 43.
Ranked second only because it is on someone else's merge schedule and our pin is
`openenv>=0.4.2,<0.5`.

### 3. Logging filter — workable, but last resort

The record is well-identified: logger `uvicorn.error`, level `ERROR`, message
`"Exception in ASGI application\n"`, `record.exc_info[1]` a
`starlette.websockets.WebSocketDisconnect`, and the traceback's **last three
frames** are exactly:

```
openenv/core/env_server/http_server.py  websocket_endpoint  1694
starlette/websockets.py                 close               181
starlette/websockets.py                 send                89
```

(Probed directly; the openenv frame is the only openenv frame in the traceback.)

So the objection *can* be narrowed a long way: match on the presence of an
`openenv/core/env_server/http_server.py` frame whose `co_name` is
`websocket_endpoint` **and** an innermost frame in `starlette/websockets.py`
`send`, rather than on the exception class alone. A real error of that exact
shape is then essentially impossible.

But it still reaches into another library's logger from `serve()`, it is silent
when it stops matching (an openenv release that renames the function or moves
the line turns the filter into a no-op and the noise returns with no signal that
it did), and it only applies where `serve()` runs — a hub-deployed world using
`openenv_app.py` and its own uvicorn gets nothing. Strictly worse than option 1
on every axis. Not recommended.

### 4. `log_level="warning"` — DOES NOT WORK

Disproven. Uvicorn logs this at **ERROR** on `uvicorn.error`, so raising the
threshold to WARNING lets it straight through. A 20-session run at
`log_level="warning"` produced **20** full tracebacks. This option is off the
table on its own merits, before the "loses the bound-port startup line"
objection is even reached — and note that `tests/serving.py:39` already uses
`log_level="warning"` and is full of them.

## Recommendation

Do **1 + the client fix**, and offer 2 upstream.

The client fix (`SeahavenClient._disconnect_async`) is the honest fix: it makes
our own disconnect well-behaved rather than hiding a symptom, it costs nothing
measurable, and it removes 517 of the 518 tracebacks our own suite generates.
The middleware closes the gap for clients we do not control, in a supported
seam, without touching anyone's logging. Together they take a `seahaven serve`
error log to zero noise from clean disconnects, with no dependence on an
upstream release.
